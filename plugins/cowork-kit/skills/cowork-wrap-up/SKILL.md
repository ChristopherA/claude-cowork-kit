# Wrap up

The session is ending and the next one, or the phone at 11pm, should start from where this one stopped rather than from nothing. Write that down, in a project doc, short enough to read in a minute. This is the write side of the where-was-i skill, which reads. It is not a capture: a capture is a thought thrown at the inbox; this is the state of the work.

## What goes in

Four parts, each a few lines, in the reader's words where you have them:

1. **Done.** What changed this session and where it is: the folder and file name, or which project doc. Nothing that is already recorded elsewhere is repeated; point at it.
2. **Open.** What was started and not finished, and what was decided but not yet done, with the reason if there is one.
3. **First next step.** One, chosen from the open items, and why that one. Not a list.
4. **Watch out.** Anything the next session would otherwise get wrong: a file that moved, a convention changed today, a question the reader wants to sleep on.

Leave out anything sensitive that a project doc should not carry: no record contents, no account details, no message bodies; point at the file in the folder instead.

## Where it goes

Show the note in full, then write it on a yes to the project doc `wrap-up.md`, replacing what was there; the old note is spent the moment a new one is written, and its "done" lines already live where they point. If the reader's project keeps a current-work section in its description doc, offer, separately, the one-line change to it that the session earned, and write that only on its own yes.

## Ending

Confirm the doc landed, read it back, and say in one line what the next session should say first: usually "where was I".

This skill is learned from Matt Pocock's handoff skill, published under the MIT license, and not copied from it.

## What this skill does not do

It does not summarize the whole conversation; it records what the next session needs. It does not file notes, edit the folder, or change the description without its own yes. It does not carry anything the project's rules keep out of project docs.

## Asking

Ask through the app's question control whenever there is a choice, and for every wait for a yes. Put up to four questions in one control when their answers do not depend on each other; a question whose answer depends on another goes in the next control. Each question offers two to four options with the recommended one first and marked as recommended; where the choices are not exclusive, allow more than one. The reader can always answer in their own words instead, and an answer in their own words outranks the options. Reflect each answer back in a phrase before going on. Never ask what the reader has already said.
