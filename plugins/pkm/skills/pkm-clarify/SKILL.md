# Clarify

Reach a decision the reader can act on, and then stop. This skill asks; it does not build. It fits any project, and it fits the knowledge project most, where the questions are small and recur: one note or three, which thread this belongs to, whether a source deserves a note at all.

## Before the first question

Look for what already decides this. Read `map.md`'s settled conventions and current work, the inbox if the decision is about a capture, and any note or thread the reader names. If something there already answers the question, say so and ask only what it leaves open. A dialogue that starts cold re-derives, worse, what the reader wrote down last month.

If the reader has already said what they want on one dimension, do not ask about it. Skip anything the request answered.

## One question at a time

For each open dimension of the decision, in the order that lets earlier answers shape later questions:

1. Say what is at stake in a sentence or two: what changes depending on the answer.
2. Give your recommendation and why, then the honest trade against the alternatives. Two or three options, never a list of everything possible.
3. Ask the one question, recommended option first, marked as recommended. If the choice has no clean options, ask in prose instead of forcing a menu.
4. Wait for the answer. Then reflect it back in your own words, name the assumption it rests on, and say if it changes a question you were going to ask.

If the reader answers with a question, or reframes in their own words, the framing was wrong. Do not repeat the same options. Say what you assumed, and ask again from their frame.

Never bundle two independent choices into one question; the reader cannot answer half of one.

## Every few decisions

Ask the question the loop cannot ask itself: does the premise still hold? Should this note, thread, or project exist at all? A run of consistent answers is not the same as a good decision; it is a sign nobody has re-opened the first one.

## Ending

When the dimensions are settled, or the reader stops, write a short summary of what was decided, each decision in one line with the reason, and what was left open. Do not start doing any of it. If something decided should be recorded, say where it would go (a convention in `map.md`, a line in a thread) and wait to be asked.

## What this skill does not do

It does not write notes, edit the folder, or change `map.md`. It does not decide for the reader by picking a default when they are silent. It does not ask more than one question per turn.
